Módulo 1: Conceptos Fundamentales (Scopes y Gates)

Antes de escribir código o pruebas, la IA necesita saber el tamaño del trabajo y cuándo detenerse a pedirte permiso. Esto lo controlan los Scopes y las Gates.

¿Qué es un Scope? (Alcance)

El scope controla cuántas de las 33 etapas del sistema se van a ejecutar. No todo cambio requiere el ciclo completo.

  • feature: Ciclo completo (33 etapas). Para funcionalidades nuevas.
  • bugfix: Ruta corta (9 etapas). Salta el diseño, va directo a corregir el código, probar y desplegar.
  • workshop: Laboratorio (26 etapas). Ideal para tu semana 1. Salta ideación, hace pruebas mínimas, y te permite aprender.
  • enterprise: Para banca o sistemas muy críticos. Máximo nivel de documentación y pruebas.

¿Qué es una Gate? (Puerta)

La IA no hace las cosas a ciegas de principio a fin. Al final de cada etapa o fase, hay una puerta de verificación (Verification Gate) donde el proceso se detiene.

  • La máquina valida la trazabilidad (ej. que no haya código sin un requisito que lo justifique).
  • El Humano decide: El sistema espera a que TÚ leas los artefactos generados y presiones "Approve" (Aprobar) o "Request Changes" (Rechazar con feedback).
  • Tu poder radica en no abrir la puerta si algo no te convence.

Módulo 2: El Flujo Completo (Las 5 Fases)

El AI-DLC es un proceso ordenado de 5 grandes fases secuenciales. Entender este flujo te ayudará a saber de dónde viene la información que pruebas y a dónde va cuando terminas.

Fase 0: Initialization (Inicialización)

El propósito: Preparar el terreno. (No interviene IA avanzada).

  • 0.1 - 0.3 Se prepara la carpeta de trabajo, se detecta qué lenguajes o infraestructura ya usa el proyecto (ej. detecta si es Node.js con AWS) y se inicia el estado de auditoría. Es instantáneo.

Fase 1: Ideation (Ideación)

El propósito: Responder al "Qué queremos hacer" y "Por qué".

Aquí se trabaja el problema de negocio antes de pensar en el código.

  • 1.1 Intent Capture: Se recibe tu instrucción y se enmarca el problema.
  • 1.2 - 1.3 Feasibility & Research: Se evalúa si es viable, si existen herramientas en el mercado o si choca con restricciones normativas de CarConnect.
  • 1.4 Scope Definition: Se raya la cancha. Qué entra y qué no entra.
  • 1.5 - 1.6 Team & Mockups: Se seleccionan los agentes de IA necesarios y se pueden hacer bocetos (wireframes) de UI.
  • 1.7 Approval & Handoff: Se empaqueta todo y se pide tu aprobación final para empezar a pensar en la solución técnica.

Fase 2: Inception (Incepción)

El propósito: Responder al "Cómo lo vamos a construir".

Aquí los arquitectos, producto y tú (QA) traducen la idea en un plan técnico.

  • 2.1 Reverse Eng.: Si el proyecto ya existe (como el tuyo en la semana 2), el sistema lee el código existente para entenderlo.
  • 2.2 Practices Discovery: La IA aprende qué reglas de equipo ya existen en el repositorio.
  • 2.3 - 2.4 Requisitos e Historias: Se escriben los requisitos formales y las Historias de Usuario (Aquí interviene QA fuertemente).
  • 2.6 Domain Design: El arquitecto diseña los componentes y bases de datos (ej. DynamoDB, SQS).
  • 2.7 Units Generation: ¡Crucial! Se descompone todo el proyecto en tareas diminutas ("Units of Work") para que los programadores las ataquen en orden.
  • 2.8 - 2.9 Contratos y Plan: Se diseñan los contratos de API y se planifica en qué orden se desarrollarán las unidades.

Fase 3: Construction (Construcción)

El propósito: Escribir el código y probarlo.

Las primeras 5 etapas se repiten por cada "Unit of Work" que se generó en la fase anterior.

  • 3.1 Functional Design: Reglas de negocio para esa pequeña tarea.
  • 3.2 - 3.3 NFRs: Requisitos y Diseño No Funcionales (velocidad, capacidad). (Aquí intervienes).
  • 3.4 Infra Design: Diseño de código de nube (Terraform, CDK).
  • 3.5 Code Generation: El desarrollador escribe el código fuente de la aplicación.
  • 3.6 Build and Test: (Tu dominio). Se compila todo el proyecto, se generan las pruebas automatizadas y se valida la calidad de lo construido.
  • 3.7 CI Pipeline: Se configuran los flujos de integración continua (Github Actions).

Fase 4: Operation (Operación)

El propósito: Llevarlo al entorno real, monitorearlo y probarlo bajo estrés.

  • 4.1 - 4.3 Despliegue: Se crea el pipeline (CD), se levantan los recursos en la nube y se ejecuta el despliegue enviando el código.
  • 4.4 - 4.5 Observabilidad e Incidentes: Se configuran paneles de monitoreo y "runbooks" por si el sistema cae.
  • 4.6 Performance Validation: (Tu dominio). Pruebas de carga extremas contra el entorno real para validar si los NFRs (velocidad) se cumplen bajo estrés.
  • 4.7 Feedback: Cierre del ciclo. La retroalimentación y los costos se documentan y vuelven a la Fase 1 para la siguiente iteración.

Módulo 3: Tu Rol Profundo como Quality Agent (QA)

Ahora que conoces todo el flujo, nos enfocaremos en tu alter ego: el Quality Agent (`aidlc-quality-agent`). Su objetivo es que nunca llegue un código roto o mal diseñado a la fase de Operación.

Etapas que Lideras (Tus momentos de brillar)

3.6 Build and Test (Construcción)

Ejecutas el proceso de construcción, generas el código de las pruebas y las lanzas contra el código que escribió el Developer Agent. Validas los "quality gates".

Tu rol humano en CarConnect:
  • Exigir la tabla de trazabilidad: Requisito → Test que lo cubre.
  • Verificar que los tests no sean "frágiles". Si un test depende de que la base de datos ya tenga un dato específico, recházalo y pide que el test sea independiente (setup/teardown).
  • Asegurar que se hayan generado pruebas de integración.

4.6 Performance Validation (Operación)

Diseñas pruebas de carga, las ejecutas en el ambiente provisionado y validas si el sistema cumple con la capacidad planificada.

Tu rol humano en CarConnect:
  • Revisar la matriz de validación NFR. El agente entregará una tabla "Objetivo esperado vs. Resultado real".
  • Si pediste que la alerta de batería dispare en menos de 500ms, aquí debes ver la evidencia. Si dice 800ms, detienes la puerta.

Etapas a las que das Soporte

En estas etapas el QA no es el líder, pero aporta su "voz" mediante revisiones cruzadas. Es vital que apruebes estas etapas asegurándote de que el QA fue escuchado.

Etapa Fase ¿Qué aporta el QA Agent? Tu criterio para aprobar (CarConnect)
2.4 User Stories Incepción Aporta la voz sobre la "testeabilidad" y redacta criterios de aceptación. No aprobar historias con criterios ambiguos ("debe funcionar rápido"). Exige criterios binarios (Sí/No).
3.2 NFR Requirements Construcción Define escenarios de atributos de calidad que se puedan probar. No aprobar NFRs sin métricas. Pregunta siempre: ¿Qué pasa si SQS reintenta? ¿A dónde van los mensajes fallidos (DLQ)?
2.2 Practices Discovery Incepción Investiga la postura de pruebas actual del equipo de forma independiente. Revisar que la IA haya detectado correctamente los frameworks de pruebas (ej. Jest, pytest) de CarConnect.

Los 5 Principios Clave del QA Agent

Estos principios son tu "Constitución QA". Úsalos el Día 14 de tu práctica para escribir las "Reglas de testing del equipo".

1. Prueba el Requisito, no la Implementación

Los tests deben validar QUÉ hace el código, no CÓMO lo hace. Si refactorizan el código, el test no debería romperse.

2. Sigue la Pirámide de Pruebas

Exige muchas pruebas unitarias (rápidas), algunas de integración (ej. Lambda -> SQS), y muy pocas end-to-end (lentas).

3. Test Driven Bugfixing

Obligatorio para la Semana 2: Cuando haya un defecto, escribir un test que reproduzca y falle por ese bug ANTES de que el desarrollador toque el código.

4. Independencia Total

Los tests no deben compartir estado. Cada test prepara su propia data y la limpia.

5. Cobertura Significativa > 100%

Un 70% de código cubierto con pruebas pensadas en el negocio es mejor que 100% con asserts inútiles.

Casos Prácticos de Debate

Caso A: El test frágil (Etapa 3.6)

El agente generó el envío a SQS y el QA hizo un test que verifica que `sqs.sendMessage` responde 200 OK. El test falla a veces cuando AWS está lento.

Tu Criterio: Rechaza en la puerta. Exige que el QA use un MOCK para SQS en pruebas unitarias, dejando las llamadas reales solo para la suite de integración.

Caso B: El Bugfix sin red (Semana 2 - Bug Real)

Lanzas `/aidlc bugfix`. En la etapa 3.5, el Developer arregla el código. En la 3.6, el QA te dice "El código compila y los tests antiguos pasan".

Tu Criterio: Rechazar. Invocando el Principio #3, exige que el QA demuestre un nuevo test de regresión específico para ese bug. Sin ese test, el fix no va a PR.

Resumen: AI-DLC es una fábrica automatizada de software con 5 naves industriales (las fases) y 33 estaciones de ensamblaje (las etapas). Como QA, tu trabajo es supervisar los puntos de control clave (Gates) y asegurarte de que el producto nunca pase a la siguiente nave si no cumple los estándares de calidad de CarConnect.
